Your code doesn't start with a cursor. It starts with a thought

You write your code. You run it. Something breaks. So you ask AI, and seconds later, the answer appears. The code works.

But here's the question: did you learn how to solve the problem, or did you simply learn how to copy the solution?

That's the question MUSE is built around. We believe AI belongs in education. But its role isn't to replace the thinking. It's to make students better thinkers, better problem solvers, and better programmers. AI should be a tutor, not a code generator.

The question

How do we make AI help students think instead of thinking for them?

You write your code.
You run it.
It doesn't work.
You ask AI.
The code works. But did you?

what happens now

When AI solves the problem before you understand it, what exactly have you learned?

A student reads "remove duplicates while preserving order" and starts typing. The assistant completes the function. The tests pass.

But nobody asked what should happen when the list is empty. The student doesn't know, because the question was never part of the process. The code works. The understanding never had a chance.

what MUSE changes

The thinking comes first. And this time, it's written down.

Before writing a single line of code, the student defines what they want to build: the inputs, outputs, edge cases, and a worked example. That specification stays locked.

Once the editor opens, the code is checked against the student's original plan. So when the student forgets to consider an empty list, it's no longer an invisible gap. It's something they can identify, explain, and learn from.

Phase 01 Specification gate

Before you write a single line of code, put your idea into words.

Not code. Not a guess at what the AI wants to hear. Your understanding of the problem.

When something is unclear, MUSE doesn't fill in the blanks. It asks questions. The editor stays locked until you've worked through the problem clearly enough to begin.

Enforced The rubric is validated in Python, not negotiated with the model. An empty examples field cannot be persuaded into counting as complete. If a required field is missing, the gate stays closed.
Guarded If the model infers information from the assignment instead of the student's own words, that information is discarded before storage. A student doesn't get credit for an answer they never gave.
Stuck? Say "I don't know." MUSE explains what the question means and gives you meaningful options to choose from. It helps you understand the decision without making it for you.
Escape Asked twice about the same genuinely ambiguous point? You can say "My answer stands." Sometimes you have a reason to keep your answer. MUSE respects that. The gate is a guide, not a bouncer.

Phase 02 Guided implementation

Now comes the code. No autocomplete. No solution waiting to be copied.

You write. And when you get stuck, MUSE doesn't take the problem away from you. Instead of saying "here's the corrected code", it asks: "what value do you expect here?"

Because sometimes the most useful answer isn't an answer at all. It's the question that helps you discover the answer yourself.

No ghost text The editor runs with autocomplete and inline suggestions disabled. Nothing writes ahead of you. Every line is yours.
Ask freely Have a question about Python? Get a direct answer. There's nothing educational about making someone struggle to understand what enumerate() does. But when you ask about your own program, MUSE helps you investigate instead of handing you the fix.
A way forward Genuinely stuck? You can request a direct hint. It's available when you need it, and it's counted as part of your session. Not as a punishment, but as a way to understand how you use assistance.

Phase 03 Reflection

When the code is finished, MUSE looks back at where you started.

What did you say you wanted to build? What did you actually build? If there's a difference, MUSE doesn't simply mark your work as wrong. It asks you to examine it.

You notice the difference. You understand it. You explain it. Then you fix it. Because writing code is only part of learning to program. Understanding your decisions is the rest.

Drift Your specification says one thing. Your code does another. And nothing in your session shows that you noticed.
Revision You changed your mind deliberately. That's completely valid. But calling something a revision requires an actual quote from your conversation. No quote, no revision.
Bug Your code is trying to do what you specified, but it isn't doing it correctly.
Required Nothing gets submitted until every difference has an explanation in your own words.

The loop

MUSE turns programming into five steps, in that order.

01 Think

Describe what you want to build, in your own words.

02 Plan

Define the inputs, outputs, edge cases, and one worked example.

03 Code

Write the program yourself. Nothing types ahead of you.

04 Reflect

Compare what your program does with what you originally planned.

05 Improve

Explain every difference. Then make the necessary changes.

For students

What you take away that a finished assignment alone can't give you.

01

The habit of deciding first

Inputs. Outputs. Edge cases. A worked example.

Before writing a line of code, you learn to define the problem. It's the same discipline behind a design document, a development ticket, and an API contract.

02

Edge cases you chose yourself

Empty inputs. Zero. Negative values.

You decide what should happen and write it down. So when your code behaves differently, you can recognize the difference between an intentional decision and an overlooked case.

03

The ability to debug independently

"What value do you expect here?"

It's a question you'll learn to ask yourself, even when the tutor isn't there.

04

The language to explain your own code

Explaining differences in your own words is a skill that carries into code reviews, stand ups, technical interviews, and everyday collaboration.

05

An honest picture of your learning habits

How many questions did you ask? How many were about Python itself, and how many were about your own program? How many hints did you use? How many drafts did your plan go through?

MUSE makes these patterns visible without turning them into a grade.

06

A record of your thinking, not just a grade

Every draft, question, and answer is preserved and readable. You can trace how your understanding developed, where you got stuck, and how your decisions changed.

A green checkmark shows completion. Your history shows the learning.

For instructors

Finally, visibility into how students think, not just whether they finished.

MUSE gives instructors insight into where students struggled, what they misunderstood, and what the class may need to explore next.

Instead of seeing thirty separate mistakes, instructors can see when an entire cohort shares the same misconception. Every difference is grouped by the concept it concerns, turning scattered errors into patterns that are easier to understand.

Class view See where students' code diverged from their own specifications. A straightforward database grouping, with no AI required at read time. The result is fast, transparent, and consistent.
Student view Explore the complete learning journey:

  • Question logs and classifications

Dependency profile

A mirror pointed at the student, and nobody else by default.

MUSE tracks how you use its help. Not to judge you. To help you recognize your own patterns.

It records
  • Total questions asked
  • Questions about Python versus your own code
  • Hints taken
  • Topics you returned to
  • Time between opening an assignment and asking for help
Not a grade Your dependency profile is never part of your mark. It's a reflection tool, designed to reveal patterns you might otherwise miss.
Not shared by default The profile is student facing by default. Instructor access requires explicit, course level opt in stored in the data model, not merely a toggle on a page. Without that permission, the instructor endpoint refuses the request outright.

Under the hood

The rules students rely on are enforced in code, not left to a prompt.

Ask a model nicely not to give away the answer, and it might still do exactly that. MUSE takes a different approach. Anything a student depends on is enforced through checks that run regardless of what the model says.

Rubric floor

An unanswered structural item is marked as unmet in Python before any model is consulted. If a classifier returns gap: null for an empty plan, the editor stays locked.

Extraction guard

If the model fills in a field using information from the assignment rather than the student's own words, that information is discarded. The extracted data is matched back against what the student actually wrote.

Sandboxed execution

Every test case runs in a fresh subprocess with a wall clock timeout. On POSIX systems, CPU, address space, and file size limits are applied.

Two providers

Mistral is the primary provider, with Groq available for failover. Both sit behind a single generate_structured() interface. A circuit breaker prevents repeated requests to a provider experiencing rate limits.

Runs offline

A deterministic stub replaces both providers during offline testing. That means the entire flow, from specification gate to tutor to reflection, can be tested without an API key or network connection.

Everything is preserved

Every specification version, gate turn, code snapshot, question, and detected difference is stored as a row. The reflection statistics are queries, not AI generated summaries.

In short

We don't want AI to write better code for students. We want it to help students become better programmers.

The future of education isn't about choosing between humans and AI. It's about designing AI to support human learning.

MUSE is deliberately different from assistants that prioritize delivering a finished solution. It won't simply hand you a function when you ask for one. Instead, it helps you understand the problem, make your own decisions, and recognize where your implementation differs from your intentions.

By the time you write the code, you should know what you're building, and know that the decision was yours.
