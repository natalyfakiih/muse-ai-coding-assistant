Technical walkthrough

MUSE Internals

How the system is built, one screen at a time: the endpoints each screen calls, what happens server side in order, which decisions are made in Python and which are asked of a model, and what ends up in the database.

Decided in Python

Deterministic. No model is consulted and no prompt can change the outcome. Everything a student's progress depends on lives here.

Asked of a model

Phrasing, classification, judgement calls. Every one of these is validated in Python before it is trusted or stored.

01

The shape of the application

One FastAPI process, two HTML pages, no build step and no frontend framework.

The server is FastAPI with SQLAlchemy 2.0 (typed Mapped / mapped_column) and Pydantic request bodies. Four routers mount under /api: specifications, tutoring, reflection, dashboard. Two routes serve HTML, / for the student and /instructor for staff, and /static and /pics are mounted as static directories.

The frontend is two hand written files, frontend/js/app.js and instructor.js, talking to the same JSON API. The only external dependency on the page is the Monaco editor loader. Phase navigation is a class toggle on three <section> elements, not a router.

Errors are mapped once, centrally

Module code raises domain exceptions and never builds an HTTP response. main.py registers handlers that turn each into a status and a message a student can read: 

# app/main.py
ProviderExhaustedError    → 503  both providers failed
MalformedJSONError        → 502  a provider broke the JSON contract
NoProviderConfiguredError → 503  no API key and no offline stub
ProfileNotVisible         → 403  course has not opted in
ValueError                → 400  a rule the student hit
LookupError               → 404
Why it matters

Every module becomes directly testable without a TestClient, and the student never sees a stack trace or a bare 500. ValueError mapping to 400 is what lets business rules read as plain raise ValueError("...") inside the modules.

Storage

SQLite by default, Postgres by changing one environment variable. The JSON columns are declared once as a variant so the same models work on both: 

# app/db.py
JSONColumn = JSON().with_variant(JSONB(), "postgresql")

On SQLite three pragmas are set per connection: journal_mode=WAL, synchronous=NORMAL and busy_timeout=5000. That last one is not cosmetic, see the call logger below.

_add_missing_columns() runs at startup and ALTERs in columns the models have gained since the file was created, so adding a field during development does not mean dropping the database and losing every session.

02

The data model

Nine tables. The important design decision is that nothing is overwritten: the record of how a student worked is the product. 

Student ──┐
          ├─ Specification (versioned, one row per draft)
Assignment┘        │
                   ├─ CodeSnapshot   every autosave + the final one
                   ├─ Interaction    every tutor exchange
                   └─ DiffResult     every difference found at submission
                            ▲
          GateTurn ─────────┘ (keyed on assignment+student, not spec)
          LLMCall             every provider call, written off-request
          CourseSettings      dependency-profile visibility per course

Specification is append only

Each clarification round writes a new row with version = previous + 1, carrying forward gap_ask_counts, confirmed_gaps, dont_know_counts and last_question. Locking sets status = "locked" on the newest row. Drift is measured against that frozen content, and the version history is what the instructor dashboard replays.

Why GateTurn is keyed differently

Every other child table points at specification_id. GateTurn points at assignment_id + student_id, because the gate writes a new Specification version on almost every turn. Keying the transcript to a specification would scatter one conversation across fifteen rows with no way to read it back in order.

03

The LLM layer

One function. Every AI call in the system goes through it, which is what makes failover, logging and the offline mode possible at all. 

# app/llm/client.py — the only entry point
generate_structured(system_prompt, user_payload, schema_hint,
                    *, task, tier, temperature=None) -> dict

schema_hint is appended to the system prompt along with "respond with ONLY valid JSON", so both providers are asked for the same shape. Prompts live in app/llm/prompts.py as (system, schema) tuples: twelve of them, one per task.

Two tiers

CLASSIFICATION tasks (extract fields, pick the next gap, classify a question) go to a small fast model. DIALOGUE tasks (anything a student reads) go to a larger one. Cost and latency follow the distinction between a label and a sentence a human will judge.

Failover, and the circuit breaker

  1. Build the provider order: primary first (MUSE_PRIMARY, default Mistral), then the other.

  2. Drop any provider whose breaker is open, unless that leaves nothing, in which case try it anyway.

  3. Only the primary gets retries. The fallback gets one attempt, because the fallback is the retry.

  4. On a rate limit: record it, open that provider's breaker, and break out immediately. No sleep, no retry.

  5. On a 5xx or timeout: sleep BACKOFF × (attempt+1) and retry.

  6. On malformed JSON: log it and raise rather than failing over.

A real bug this fixed

The dashboard showed every one of 114 Mistral calls returning 429. Each one was costing ~530ms to fail, then a 1500ms sleep, then another ~530ms, before Groq was even tried. Every call in the app paid that, and the whole thing felt broken rather than slow.

The breaker took mean call latency from about 4.0s to about 1.5s. The fix was not a faster model, it was noticing that we were politely retrying a provider that had already said no.

Why malformed JSON raises instead of failing over

A provider that answers but breaks the schema is a prompt regression, not an outage. Failing over would silently paper over it and we would ship a broken prompt that "works" because the fallback happens to cope. Raising makes it visible in the ops log the moment it starts.

Call logging, off the request path

Every call emits a CallRecord to registered sinks. main.py registers one that pushes onto a queue drained by a background thread with its own session.

Why a thread and not a plain insert

The first version wrote the llm_calls row inside the request's own transaction. SQLite gave database is locked under any concurrency, because the logger had opened a second write transaction while the request still held one. Moving the writer off-request plus busy_timeout=5000 fixed it. Registration is idempotent, since the first version appended the same sink on every reload and produced duplicate rows.

Screen 1 · Specification gate

Chat on the left, rubric and the growing specification on the right. The editor is unreachable until every rubric item is answered.

MethodPathDoes

One turn, in order

  1. llmextract_fields sends the student's message, the current specification and the question they were answering. The last of those matters: without it a reply like "an empty list" is stored bare, having lost the condition it applies to.

  2. py_guard_extraction() throws away anything the model did not get from the student.

    # an input needs the student to have named it, or to have
# said the function *takes* something
if not named and not _INPUT_SIGNAL.search(message):
    continue

# an output needs a verb: returns / gives / produces / ->
if not _RETURN_SIGNAL.search(message):
    continue

# an example's two sides must each appear in the source text,
# checked separately: "n=3 -> [0,1,1]" has the arrow between
if any(side and side not in flat for side in sides):
    continue

  3. py_meaningful_change() decides whether this turn produced a new version. If so, _new_version() writes one, carrying the counters forward.

  4. pynext_gap() runs the structural floor first. Items mapped to a specification field are judged by field_satisfied() with no model vote at all:

    if field == "goal":    return len(str(value).split()) >= 3
if field == "inputs":  return any(i.get("name") and i.get("type") …)
if field == "outputs": return any(o.get("type") …)
if field == "examples": return any(input and output …)

    llmOnly semantic items ("what happens when n is 0") reach the model, and its answer is checked against the rubric before it is trusted.

  5. llmgenerate_clarifying_question() phrases the question. pyThen _question_addresses_gap() checks the question is actually about the gap being scored, and swaps in a deterministic one built from the starter code signature if it is not.

  6. pyWrite a GateTurn, bump gap_ask_counts[gap_id], commit, return the payload.

writes: Specification (new version, when the turn changed anything) · GateTurn (always)
Three bugs that shaped this screen

The first three items ticked themselves. One vague opening sentence and goal, inputs and outputs were all marked answered, because the model had filled them in from the assignment text. That is the exact failure the rubric exists to prevent. Hence the extraction guard.

An item matched on its own id. required_field() was matching the substring input inside the rubric id empty_input, so a question about edge case behaviour was treated as the inputs field and ticked off as soon as inputs were filled. Fixed by matching on the item's text only, with word boundaries, plus a semantic marker regex that catches conditional phrasing, plus an explicit "field" key in the seed rubrics.

The question did not match the gap. The gap was goal but the model asked about input and output types. The student answered what was on screen, correctly, and was told it did not settle it, because it was scored against a gap the question had nothing to do with. That is the single most enraging way this screen can fail. Hence step 5.

"I don't know" and "my answer stands"

gap_kind_for() classifies the gap as type, example, statement or decision, and that decides what the button may legitimately offer. A decision has real alternatives. An example has to come from the student, so the most that can be offered is a shape to fill in. A goal has nothing to offer at all, so options are forced empty in code.

The one that caused the most swearing

Clicking an option the system itself had offered was rejected as wrong. The offered answer was "It takes a list of integers", but the rubric wanted a name and a type. signature_params() now parses def dedupe(items) out of the starter code, and _normalise_options() appends "called items" to any option for a rubric item that asks for a name. The system cannot offer an answer it will then mark wrong.

The editor

Monaco with every suggestion mechanism switched off. Six settings, because turning off one of them leaves the others happily completing: 

quickSuggestions: false,          suggestOnTriggerCharacters: false,
wordBasedSuggestions: "off",      acceptSuggestionOnEnter: "off",
tabCompletion: "off",             inlineSuggest: { enabled: false }

A plain <textarea> fallback takes over if the CDN loader fails, so a flaky network downgrades the editor rather than ending the session.

One tutor message, in order

  1. pyRefuse unless the specification is locked. The tutor does not exist before phase 2.

  2. pySave a snapshot if the code changed, and compute a unified_diff against the previous one. The classifier sees the diff, not the whole file.

  3. llmclassify() returns factual or problem_solving with a confidence and a reason.

  4. pydeterministic_override() extracts identifiers from the student's actual code and forces problem_solving if the message names one. "What does enumerate do" is factual; "what does my_result do" cannot be, whatever the classifier says.

  5. llmFactual questions get answer_factual(), which can return deflect: true if the question turns out to be answerable only from the student's own code. The message is then re-routed as problem solving.

  6. llmProblem solving gets socratic_question(), which receives the previous counter questions in this thread so it does not ask the same thing twice.

  7. pyWrite the Interaction with its classification, confidence, reasoning, mode and thread_round. The escape hatch unlocks once thread_round >= TUTOR_ESCAPE_HATCH_ROUNDS.

writes: CodeSnapshot (if changed) · Interaction (always, with assist_cost=1 for a hint)
Two safety nets around one classifier

The override before and the deflect after both exist because a small classification model will confidently call "why is my loop wrong" a factual question. One model call, two deterministic chances to catch it, in opposite directions.

On submit, a diagnostic thread per failure

Submitting runs the reflection pipeline but the student stays on this screen: each failing case gets a diagnostic_question, already computed, and a reply box. discuss() continues that thread, DiffResult.id keyed via Interaction.diff_result_id. There is a test that fails if a generated diagnostic question contains a giveaway token from the solution.

Screen 3 · Reflection

Differences on the left, the behavioural diff and session statistics on the right. Nothing is accepted until every difference has an explanation.

MethodPathDoes
POST/api/specifications/{id}/submitrun the pipeline
POST/api/diff-results/{id}/explanationrecord the student's words
POST/api/diff-results/{id}/discusscontinue a diagnostic thread
GET…/session-statscounts and transcript, no AI
POST…/finalizeaccept the submission

Submission, in order

  1. pyRefuse unless the spec is locked and the rubric declares an entry_point.

  2. pyRefuse if the specification declares no examples and no edge cases. There would be nothing to run the code against, and returning a clean bill of health would be a lie: the code was never checked against anything.

  3. pyDelete the previous DiffResult rows. Re-submitting replaces the verdict rather than stacking a second one on top.

  4. llmmaterialize_edge_cases() turns prose edge cases ("an empty list returns an empty list") into runnable calls (items=[] with expected []).

  5. pyRun every declared case through the sandbox and build a row per case: input, expected, actual, type, error, pass or fail.

  6. llmFor each failure, classify_discrepancy() gets the case and the student's interaction log, and returns drift, revision or bug with an evidence quote.

  7. llmPre-compute the opening diagnostic_question so the card is ready before the student reads it.

writes: CodeSnapshot (is_final=True) · DiffResult per failure, with test_detail as JSON
Why "revision" needs a quote

The three categories are not equally easy to assign. Drift and bug can be read off the test result. Revision is a claim about intent, and the prompt forbids it without an actual quote from the interaction log. Otherwise the model gives everyone the benefit of the doubt, and "they probably meant to" is exactly the judgement an AI should not be making about a student's work.

The grader bug that was worse than a wrong answer

A student's specification declared the example 1,1,2 → 1,2. The runner parsed 1,1,2 as three positional arguments and called dedupe(1, 1, 2), which raises TypeError. Separately, 1,2 literal-evals to the tuple (1, 2), which never equals the list [1, 2]. The failure message read expected '1,2', got '1,2'.

She rewrote a correct function into def dedupe(*args, items=None) returning ",".join(...) to satisfy the harness. A tool whose entire purpose is "make the code match the specification" had pushed a student into deforming correct code to fit a broken grader. Three fixes: arity aware argument parsing from the function's own signature, list/tuple leniency in the comparison, and a failure message that names the types when the two values read alike.

Session statistics

app/modules/stats.py makes no LLM calls at all. It counts specification versions, gate turns, questions by classification, hints, cases run and failed, and merges GateTurn and Interaction rows into one time ordered transcript. A number a student is shown about themselves should be a query, not a generation.

Class tiles, the divergence table, the provider log, the student list, and one student in depth.

MethodPathDoes
GET/api/courses/{id}/analytics/class-patternsthe divergence table
GET/api/courses/{id}/students/{sid}/overviewone student, everything

pyclass_patterns() is a single GROUP BY over DiffResult joined to Specification and Student, counting distinct students per (spec item, category) pair. No model, no cache, no inference. That is what makes the page fast and what makes it give the same answer twice. 

select(DiffResult.spec_item_key, DiffResult.category,
       func.count(func.distinct(Specification.student_id)),
       func.count(DiffResult.id))
  .join(Specification).join(Student)
  .where(Student.course_id == course_id)
  .group_by(DiffResult.spec_item_key, DiffResult.category)

llmnarrative_summary() is the only model call on this screen, and it fires on a button. It is scoped to one assignment deliberately: without that scope, specifications across every assignment sort together and specs[-1] silently lands on the wrong one, producing a summary that quotes one assignment's prompt while grounding itself in another's differences.

The visibility rule is in the data model, not the UI

profiler.profile(..., viewer="instructor") raises ProfileNotVisible unless CourseSettings.dependency_profile_visibility is instructor_opt_in. The API returns 403. There is no hidden div and no disabled button: a dashboard that merely declines to render something is not a privacy guarantee, it is a CSS rule.

Demo data

app/demo.py writes a cohort's worth of work with no LLM calls and a seeded RNG, so the dashboard has something to aggregate and two runs produce the same database. The failures are deliberately clustered: a table of eight students failing eight unrelated things would be unreadable, and the panel exists to surface the thing half the class got wrong. A test asserts all three categories appear, that every demo revision carries the quote that justifies it, and that the cohorts are actually distinguishable.

08

The sandbox

Running arbitrary student code is a correctness and safety requirement regardless of scale.

Each case runs in a fresh subprocess: python -I -S _runner.py in a temporary working directory, with a scrubbed environment and the student's code written to solution.py. -I keeps the script directory off sys.path. The result comes back as JSON after a __MUSE_RESULT__ marker on stderr, which survives anything the student prints to stdout. 

# POSIX only, via preexec_fn
setrlimit(RLIMIT_CPU,   (cpu, cpu))
setrlimit(RLIMIT_AS,    (memory, memory))
setrlimit(RLIMIT_FSIZE, (1 MiB, 1 MiB))
setrlimit(RLIMIT_NPROC, (64, 64))
os.setsid()
Honest limitation

Windows has neither resource nor preexec_fn, so on Windows you get the wall-clock timeout and a scratch directory and nothing else. A negative return code is decoded back to a signal name, so SIGXCPU reads as "hit the CPU limit" rather than as a mystery crash. For real grading, run it on Linux or in a container.

09

Testing without a network

USE_FAKE_LLM=1 (or simply having no API key) routes generate_structured() to a deterministic stub in app/llm/fake.py that implements all twelve tasks by pattern matching on the payload. The entire flow — gate, tutor, sandbox, reflection, dashboard — runs end to end with no key and no network, and the stub still logs a CallRecord with provider="fake" so the ops view tells the truth about what served.

150 tests, all offline. The ones worth knowing about assert behaviour rather than output: that a diagnostic question contains no giveaway token, that a demo revision always carries its evidence quote, that the extraction guard drops model-invented fields, that parse_call_args reads a bracketless list as one argument for a one-parameter function.

The stub bit back once

A long run of tests passed against the stub while the live system behaved differently, because the stub and the real prompts had drifted apart. Twice, the fastest way to find a real bug was to copy the live muse.db and query it: that is how we found every call was hitting the offline stub (uvicorn had started before .env existed, and --reload watches .py, not .env), and how we found all 114 Mistral calls were 429s. Both root causes would have been very hard to guess.
